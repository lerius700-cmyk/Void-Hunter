## 1. Why a second round

Round one was an EVENT: the repository was measured, pruned and archived,
and the findings were recorded. It was not a RULE. Nothing measured the
weight, so nothing noticed when the same build accumulated 8.58 GB.

Three things were left on the table, all measured:

1. **61 MB of generated cache shipped inside every binary.** The
   `_lp600.wav` is a *filtered copy* of the gameplay track, produced by
   the pause-screen lowpass. It was committed, bundled into the `.exe`
   and has been carried ever since.
2. **The filter cache never persisted.** The filtered track is written
   next to its source, which in the onefile build is `_MEIPASS` — a
   temporary directory wiped when the process exits. The 8-second
   computation is paid on the first pause of *every session*, which is
   exactly why the WAV was bundled in the first place.
3. **Nothing watched the weight.** No metric, no test, no ceiling.

And the work of round one is still sitting on 23 unpushed commits, with
the pushed release line 23 commits behind.

### 2.2 The WAV is an output, and numpy is already in the binary

`src/audio/synth.py::apply_lowpass_to_wav` is the only numpy consumer
in the audio path. It imports numpy **locally** and degrades on
`ImportError` — but PyInstaller's static analysis finds a local import
just the same, so numpy is in the bundle:

```
$ python -c "from PyInstaller.archive.readers import CArchiveReader; ..."
entradas numpy en el .exe: 39      # numpy 2.4.6.dist-info, ...
```

`build.spec` says so itself, and was right:

> BLOQUE 58.14: pre-generated lowpass-filtered BGM (avoid 8s delay on
> the first pause). Generated by tools/debug_lowpass.py from the
> original WAV at 600Hz cutoff. **Safe to omit — the game will
> regenerate on first pause if missing.**

The generator exists: `tools/debug_lowpass.py`.

So the WAV is a **cache**, and the binary already carries everything
needed to rebuild it.

### 2.3 Where the cache is written today (the latent defect)

`src/audio/music.py::_ensure_filtered_bgm` writes the filtered track
next to its source:

```python
src_dir = os.path.dirname(str(src_path))          # <_MEIPASS>/Assets
out_path = os.path.join(src_dir, "...gameplay" + suffix)
```

In the onefile build `src_path` lives in `_MEIPASS`, a temporary
directory that is deleted when the process exits. The cache is
therefore **thrown away every time**, and the 8-second computation is
paid again on the next run.

The onedir build is not affected: its `_internal/Assets` survives.

### 2.4 The trap in the obvious fix

`_find_assets_dir()` probes, **in this order**:

1. `<exe_dir>/Assets/`
2. `<exe_dir>/_internal/Assets/`
3. `<_MEIPASS>/Assets/`
4. `<_MEIPASS>/_internal/Assets/`
5. `<project_root>/Assets/`

It returns the FIRST directory that exists. A cache written into
`<exe_dir>/Assets/` would therefore **become the assets directory**, and
the game would stop finding the original gameplay track: the music
would break. The cache must live somewhere else.

### 2.5 The history is left alone

Of the 282 MB of WAV blobs in the whole history, 159 MB are the two
REAL tracks (the gameplay music and the title music) and **122 MB are
the two generated ones**. Purging them would shrink `.git` from 504 MB
to ~382 MB — at the price of changing every commit hash, orphaning the
published tags and force-pushing the release branch.

> **Decision: the history is NOT rewritten.** The tags `v1.7.0`,
> `v1.7.2` and `v1.8.0` stay exactly where they are, and the release
> branch keeps its identity.

## 4. The design

### 4.1 A cache that persists

The filtered track is written to a dedicated, writable directory next to
the executable, and it is **read before it is generated**:

```
<exe_dir>/_vh_cache/keep kept - Lerius - soundtrack gameplay_lp600.wav
```

`_vh_cache` is NOT `Assets`, for the reason in §2.4: a directory called
`Assets` next to the executable would shadow the bundle's own.

The resolution order for the cache directory:

1. `<exe_dir>/_vh_cache/` — next to the executable. Survives the
   process, so the 8 seconds are paid **once**, not once per session.
2. The directory of the source track — today's behaviour. Used when the
   executable sits somewhere read-only (Program Files): the filter
   still works, it just does not persist.
3. Nowhere — the filter is skipped and the game runs without the pause
   effect. It never crashes.

The file is generated to a temporary name and moved into place
atomically, so an interrupted run cannot leave a truncated WAV that the
next run would happily reuse.

### 4.2 The binary that shrinks

- `build.spec` drops the `_lp600.wav` data entry.
- The WAV is untracked (`git rm --cached`). It stays on disk and is
  already covered by `Assets/*_lp*.wav` in the release line's
  `.gitignore`.
- The `.exe` goes from **278 MB to ~217 MB**.
- The pause filter keeps working: numpy is in the bundle.

**What the user sees:** the first pause of the first run of a new
installation takes ~8 seconds while the track is filtered and cached
next to the `.exe`. Every later run is instant. Today it is the
opposite: the binary carries a 61 MB copy so that no run pays the
delay.

### 4.3 A budget that holds

`tools/repo_budget.py` measures three things and prints them as a
report:

| Metric | How it is measured | Ceiling |
|---|---|---:|
| Tracked tree | the size of every path `git ls-files` names | 300 MB |
| Build output | the size of `dist/` | 600 MB |
| History | the size of `.git/` | 550 MB |

`tests/test_repo_budget.py` runs the measurement and fails when a
ceiling is crossed. The `dist/` ceiling is the one that catches the
failure that actually happened: 8.58 GB of accumulated builds, unnoticed
for months.

The three numbers become rows in the `STATUS:GENERATED` block, so the
weight of the project is visible in the file every agent opens.

The ceilings live in one place — `tools/repo_budget.py` — and are
raised deliberately, never by editing a test.

## 6. Risks

| Risk | Mitigation |
|---|---|
| The cache shadows the assets directory | the cache is `_vh_cache`, never `Assets`; §2.4 explains why, and a test asserts the source track is still found |
| An interrupted generation leaves a truncated WAV | it is generated to a temp name and moved atomically into place |
| The `.exe` lands in a read-only directory | the cache falls back to today's behaviour; the filter degrades, the game does not crash |
| The first pause is visibly slow for a new user | it happens once per installation, and the alternative (a 61 MB copy in every download) is what the round was about |
| The budget test fails on someone else's machine | the ceilings are about the repository, not the environment: `.venv`, `.worktrees` and the archive are excluded |
